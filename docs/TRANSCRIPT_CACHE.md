# 会话缓存（OpenCode）

打开会话时先显示本机保存的内容，再只向服务器读取新增的部分；本机内容在使用前会和服务器核对，对不上就丢弃重读。服务器始终是权威数据源，缓存只是一份经过核对的副本。DeepSeek Harness（DSH）的协议每次打开都下发完整快照，仍沿用 `OfflineCache` 的快照缓存，不在本文范围内。

## 存什么

- 位置：应用私有目录下的 SQLite 数据库 `transcripts.db`（`core/TranscriptStore.kt`）。数据库在第一次使用时于后台线程打开，不拖慢启动。
- 内容：服务器 `GET /api/session/{id}/message` 返回的**原始 JSON**，一条消息一行。读取时走与联网时相同的 `toMessage()` 解析，所以缓存显示与服务器显示完全一致；以后 `Message` 新增字段也不会因为缓存而丢失。
- 只存**已结束**的消息（`isSettledMessage`）：助手消息已完成且所有工具调用已结束、shell 已退出、上下文整理已结束、没有仍在后台运行的子任务。还会变化的消息永远从服务器重读。
- 每个会话保存的是服务器时间线中**连续的一段**：从最早保存的那条到“水位”（最新保存的一条），中间没有空洞。
- 内嵌的 `data:` 大块内容（截图、手机上传的文件）不保存，替换为占位标记，界面显示“附件 · 未缓存，联网刷新后显示”，不会显示成损坏的附件。
- 加密：每行先压缩再用 AES-GCM 加密，数据密钥由 Android Keystore 包裹保存。密钥无法解开时（例如从备份恢复到新设备）整库作废重建。
- 容量：总量超过 64 MB 时按“最近打开时间”淘汰最久未用的会话；正在打开的会话不会被淘汰。设置 → 关于与诊断 → “清除会话缓存”可随时清空。

## 打开会话的流程

1. 立即从本机显示最新约 120 条（向前补齐到一轮对话的开头），没有缓存时显示加载骨架。
2. 后台只读最新一页：会话的 `time.updated` 没变时读 10 条，变了读 50 条；新增很多时再按 200 条一页往前读，直到碰到水位（最多 4 页）。
3. 核对后合并：
   - **校验通过**：水位那条消息还在服务器上，读到的这一页与本机重叠的部分 id、顺序完全一致，每条的显示内容指纹一致 → 只把新增的已结束消息追加进缓存。
   - **更正**：顺序一致但某条消息服务器现在显示得不一样 → 按服务器内容改写这几行，并记入诊断。
   - **重建**：水位消息不见了（撤销 / revert 删掉了尾部）、顺序对不上、或者新增太多读不到水位 → 丢弃这段缓存，用这次读到的内容重建。
4. 往上翻历史时先读本机（离线也能翻），本机读完再用保存的服务器游标继续向服务器要更早的消息，读到的也会接进缓存。

会话运行中，实时事件触发的尾部回读也会把新结束的消息接进缓存；但如果这一页够不到水位（中间有没读到的消息），就不写，留给下次打开时补齐，绝不跨过空洞拼接。

## 为什么只核对最新一页就够

OpenCode 2.x 按插入序号排列时间线（`packages/core/src/session/store.ts`）：新消息只会追加在末尾；撤销删除的是从某条消息到末尾的整段，水位一定在被删的范围内。所以“水位还在、重叠部分一致”就说明本机这段没有被改动。

剩下的风险是服务器改写了很早以前的消息（正常情况下不会发生）。为此每个会话大约每 7 天、在不计流量的网络下，打开后会在后台把整段缓存和服务器逐条比对一次（`TranscriptSync.verifyAll`），不一致就丢弃该会话缓存并重新读取当前会话。

## 不会出错的保证

| 风险 | 处理 |
|---|---|
| 会话在读取过程中被删除 | 每次写入都带读取开始时的会话“纪元”，删除会推进纪元，晚到的写入被丢弃，不会把删掉的会话写回来 |
| 两次读取并发写同一会话 | 追加时必须与读取时看到的水位一致，否则放弃 |
| 服务器地址或账号改了 | 缓存按“协议 + 地址 + 用户名”绑定服务器，变化即清空该服务器的缓存 |
| 解析规则升级 | 数据库记录格式版本，不一致即整库作废 |
| 单条消息过大 | 超过约 1 MB 的消息不保存，缓存在它之前截止，之后的内容照常从服务器读取 |
| 服务器游标失效 | 游标只用服务器下发的，不自己拼。保存的“更早历史”游标锚定在缓存最早一条消息上，这条被删只可能是整段都被撤销，此时水位也已消失，下次打开会重建 |

## 诊断

设置 → 关于与诊断 → “复制诊断信息”会附带一行统计，例如：

```
会话缓存：首次 3 · 校验通过 12 · 更正 0 · 重建 1 · 完整校验 2（不一致 0）
```

“打开会话”一行里还有本次打开的请求数和下行字节数。如果“更正”或“不一致”长期不为 0，说明服务器的行为与上面的假设不符，需要反馈。

## 弱网对比

单元测试 `TranscriptOpenBenchmarkTest` 用每个请求延迟 300 ms 的模拟服务器打开同一个工具调用密集的会话（40 轮、每轮 31 条消息）：

| 场景 | 耗时 | 请求 | 下行 |
|---|---|---|---|
| 旧实现 | 约 2000 ms | 6（依次） | 114 KB |
| 首次打开（无缓存） | 约 830 ms | 2 | 66 KB |
| 再次打开，无新消息 | 约 350 ms | 1 | 9 KB |
| 再次打开，新增一轮 31 条 | 约 370 ms | 1 | 47 KB |

这些是模拟数值，真机效果以诊断信息里的“打开会话”记录为准。

## 评估过但没有做的

- **DSH 增量读取**：`session/follow` 的首帧是完整快照（`records` + `hasMore`），本仓库记录的协议里没有“从某个游标之后继续”的参数；而且这一帧同时建立实时订阅，本来就必须读。要做增量需先确认上游协议是否支持断点续读。
- **会话列表增量**：首页列表已经先显示缓存，再用一个与其他启动读取并行的请求刷新首页，增量只能省字节，省不了往返。
- **图片 / 文件磁盘缓存**：会话里的图片是内嵌 `data:` 或外部链接；文件浏览读取的是会变化的工作区内容，缓存会带来显示过期文件的风险，与“缓存必须准确”的要求冲突。
